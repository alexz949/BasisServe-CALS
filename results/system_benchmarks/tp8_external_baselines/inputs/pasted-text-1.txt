===============================================================================

This experiment is about:

    + decode

ALS-full may also be collected if it is essentially free, but it is not

SHADOWKV SEMANTICS
------------------
Preserve the original ShadowKV global-K SVD semantics.

For Llama-3.1-8B-Instruct:
    H_kv = 8
    head_dim = 128
    TP = 8

Each TP rank owns one local KV head after prefill:

    K_p: [B, T, 128]

ShadowKV's original decomposition acts on the concatenated K:

    K_global = concat(K_0, ..., K_7)
             = [B, T, 1024]

and computes a rank-160 decomposition.

DO NOT replace this with 8 independent per-rank SVDs.
That is a different algorithm.

Implement the TP8 construction as:

For transformer layer l:

    owner = l % 8

    1. Each rank produces its local pre-RoPE K_p normally.
    2. Gather the 8 local K shards to `owner`.
       Prefer gather-to-owner / explicit send-recv over all-gather-to-all.
    3. Owner concatenates them to [B, T, 1024].
    4. Owner computes ONE rank-160 ShadowKV SVD per request.
    5. Redistribute factors:
           shared U [B, T, 160] -> broadcast to all ranks
           local SV_p [B, 160, 128] -> each rank receives only its own shard
    6. Free the temporary full [B, T, 1024] K buffer immediately.
    7. Each rank subsequently runs ShadowKV decode locally:
           local Q
           local landmarks / retrieval
           selected U rows
           local SV_p
           reconstruct local selected K
           local selected V / CPU-offload path
           normal TP output collective

Do NOT perform an additional cross-rank K gather during decode.

Rotate the owner by layer (l % 8) so the global SVD work and temporary memory
are not always assigned to rank 0.

For large B, it is acceptable and preferred to process the SVD per request
rather than forming one enormous [B,T,1024] temporary tensor, as long as this
is mathematically equivalent to independent per-request ShadowKV SVDs.

Use ShadowKV's paper-faithful:
    rank = 160
    chunk_size = 8
    sparse budget = the configuration already used in our ShadowKV quality
                    protocol / official CPU-offload implementation

Do not modify the retrieval algorithm to match BasisKV's exact support.

EXPERIMENT 2: STAR-KV V-only TP8 GPU-memory / OOM behavior
===============================================================================

GOAL
----
Measure how a STAR-KV-style shared low-rank VALUE representation behaves
under TP8 compared with source-local BasisKV Value compression.

THIS IS A V-COMPRESSION-ONLY EXPERIMENT.

Do NOT enable:
    BasisKV Key routing
    ShadowKV routing
    STAR-KV K compression

All methods use:
    dense exact K
    full attention

We only change the Value representation.

LABEL THE BASELINE CLEARLY
--------------------------
Use the label:

    "STAR-KV V-only"

or

    "STAR-KV Value compression"

Do not present it as the complete STAR-KV method if K compression is disabled.

METHODS
-------

       local V width / TP rank = 128

2. BasisKV V96 / ALS-full
       source-local width / TP rank = 96

3. BasisKV V64 / ALS-full
       source-local width / TP rank = 64

4. STAR-KV V-only, 75% retained
       original global V width = 1024
       shared latent rank rV = 768
       replicated on every TP rank

5. STAR-KV V-only, 50% retained
       original global V width = 1024

       replicated on every TP rank

If actual STAR-KV exported ranks differ from these nominal targets, use the

STAR-KV TP8 SEMANTICS
---------------------
Preserve STAR-KV's layer-wise shared Value latent.

For each layer:

    V_c = X W_V_low
        shape [B, T, rV]

The latent is shared across all KV heads.

Under TP8, to preserve this factorization while allowing each rank to compute
its local attention output without per-token cross-rank communication:

    replicate the complete V_c on every TP rank

Each rank stores only the decoder/up-projection slice required to recover its
local Value/output contribution.

DO NOT silently replace this with 8 independent local low-rank decompositions.
That would be a different algorithm.

The intended per-token V-state widths per GPU are therefore approximately:

    Dense TP8:
        128

    Basis V96:
        96

    Basis V64:
        64

    STAR-KV 75%:
        768

    STAR-KV 50%:
        512

The purpose of the experiment is precisely to measure the resulting TP8
placement behavior.

FAIRNESS
--------
Dense K is identical in all arms.

Do not count model weights differently between methods.

Do not introduce CPU V offload for one method unless all compared methods use
the same policy.

Use BF16 Value-cache state for all methods.

Use the same attention/backend wherever compatible.

This is NOT a speed benchmark for STAR-KV.
Do not optimize the figure around latency.
The primary endpoint is GPU-resident memory / capacity.

PREFILL DESIGN

IMPORTANT: Do not let a giant one-shot prefill temporary tensor dominate the

The existing fixed runner can fail at ~128K/B16 because of a large temporary

For this experiment implement/use a bounded-memory chunked prefill path for
ALL arms, with the same chunk size, e.g.:

    prefill chunk = 4096 or 8192 tokens

Choose one value after a smoke test and freeze it for all formal runs.

The benchmark must distinguish:

    cache/state OOM

from

    unrelated transient prefill workspace OOM

If a failure is caused by transient prefill workspace, record it separately
and do not describe it as a KV-cache capacity limit.
